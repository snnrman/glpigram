# GLPIgram — передача обслуживания

Документ для агента (и человека), который продолжает поддерживать бота.
Здесь то, чего **нет** в коде и git-истории: устройство стенда, живые
особенности GLPI, грабли и открытые хвосты. Устройство самого бота — в
`CLAUDE.md`, что менялось — в `CHANGELOG.md` / `CHANGELOG.ru.md`.

Состояние на 28.09.2026: версия в `pyproject.toml` — 0.4.0 (накопленные
изменения лежат в разделе `[Unreleased]` changelog'а), 373 теста зелёные,
`main` синхронизирован с обоими remote.

---

## 1. Что это

Telegram-бот техподдержки поверх GLPI 11: сотрудник создаёт заявку и общается
по ней в личке с ботом, техники работают из группы поддержки, всё живёт в
GLPI как обычные Ticket/ITILFollowup/ITILSolution — бот не заводит свою
параллельную систему учёта.

Аудитория: ~97 привязанных сотрудников, ~6 техников, 380+ заявок проведено
через бота.

```bash

```

## 3. Конфигурация (`.env`)

Ключи: `TELEGRAM_BOT_TOKEN`, `TECH_GROUP_CHAT_ID`, `GLPI_API_URL`,
`GLPI_APP_TOKEN`, `GLPI_USER_TOKEN`, `GLPI_TIMEOUT`, `CATEGORY_CACHE_TTL`,
`DB_PATH`, `LOG_LEVEL`, `TZ`, `WELCOME_MESSAGE`, `TECH_GROUP_ID`,
`LEAD_LOGINS`, `ACCESS_CATEGORY_ID`, `APPROVAL_REMIND_HOURS`.
Полное описание каждого — в `.env.example`.

Что важно знать про значения на проде:

- `TECH_GROUP_ID=4` — **группа GLPI**, членство в ней = права техника в боте
  (`is_tech`, перепроверяется раз в 5 минут). Новому сервисному инженеру
  мало добавить в группу: нужен ещё профиль Technician (`profiles_id=6`) в
  его учётке GLPI, иначе «нет прав» при действиях.
- `ACCESS_CATEGORY_ID=10` — категория «Учетные записи» (переименована из
  «Учётки и доступы», чтобы не путали с кнопкой). Туда падают запросы из
  «💳 Платные сервисы».
- `LEAD_LOGINS` — список логинов лидов через запятую (26 шт.). Лид попадает
  в список выбора, **только если он сам нажал `/start` и привязался**.
- `TZ=Europe/Kaliningrad`, рабочие часы 09:00–18:00, пн–пт. Вне их всё,
  кроме уровня «🔴 Срочно (прод)», откладывается до утра.

После правки `.env` — обязательный `systemctl restart glpi-tgbot`.

## 4. Особенности GLPI REST API (проверено вживую, не по документации)

Это главное, ради чего написан документ: API GLPI 11 ведёт себя не так, как
написано в его же доках.

1. **Мёртвая сессия отдаёт 400, а не только 401.** Клиент переинициализирует
   сессию на обоих кодах (`ERROR_SESSION_TOKEN_INVALID`).
2. **`POST /Document` возвращает 201 даже когда файл не сохранён.** Если
   расширение не зарегистрировано в Setup → Dropdowns → Document types, GLPI
   создаёт пустую заглушку, а отказ прячет в `upload_result.filename[0].error`
   («Тип файла не разрешен»). Клиент это ловит, чистит заглушку и бросает
   `GlpiDocumentRejected`. Так в заявке #349 молча пропал SSH-ключ `.pub`.
   Зарегистрированы: pub, md, key, pem, yaml, yml, json, log, conf, ini,
   toml, sh, ps1, crt, cer.
3. **`TicketSatisfaction` обновляется по id ЗАЯВКИ**, а не по id строки
   опроса (`PUT /Ticket/{tid}/TicketSatisfaction` с `input.id = tid`). Иначе
   `ERROR_GLPI_UPDATE`. Строка опроса создаётся синхронно при закрытии.
4. **`TicketValidation` может ответить только та учётка, на которую он
   выписан.** Ответ «от имени» молча игнорируется. Поэтому согласование
   выписывается на сервисную учётку бота (`get_session_user_id`), а реальный
   согласующий пишется в `comment_validation` и отдельным followup.
   Удаление валидации оставляет `global_validation=4` — сбрасывать вручную
   через `PUT /Ticket {global_validation: 1}`.
5. **`users_id_supervisor` в GLPI не заполнен** (1 из 47) — иерархию «кто
   чей лид» строить по нему нельзя, она живёт в таблице `user_leads` бота.
6. Заявитель — это связь `Ticket_User` типа 1, а не колонка заявки.

## 5. Логика, которую легко сломать, не зная о ней

- **Курсор followup.** Бот пишет комментарии от сервисной учётки, поэтому
  sync-цикл не отличает их от «чужих» и заэхоил бы их обратно заявителю.
  Каждый раз после `add_followup` из бота **обязательно**
  `repo.set_ticket_followup_cursor(ticket_id, followup_id)`.
- **Карточка в группе** — одно сообщение на заявку, перерисовывается целиком
  на каждое событие (`CardService.record_event`). Неудавшийся edit не
  страшен: следующее событие само себя вылечит. События, пришедшие ДО
  отправки карточки, буферизуются в `card_pending_events` и накладываются в
  `register()` — иначе теряются (так пропало «Согласовано» в #359).
- **Нет экрана подтверждения в `/new`.** Он был, люди останавливались на
  «Готово», думая, что заявка ушла. Последний шаг (вложения) и есть
  отправка. Не возвращать.
- **Оценки решения — 4 балла без нейтральной середины** (😞😕🙂🤩 → GLPI
  1/2/4/5). Низкая оценка **намеренно** не пингует группу.
- **Ответ реплаем** на любое сообщение бота, где есть «№N», уходит
  комментарием в заявку N. Зарегистрирован раньше «создать заявку из текста»
  в `new_ticket` — порядок роутеров в `main.py` значим.
- Диалоги — только в личке (`router.message.filter(F.chat.type == "private")`),
  иначе бот реагировал бы на болтовню в группе.

## 6. Эксплуатация: что уже ломалось

- **GLPI лёг из-за маркетплейса (24.09).** Запрос к
  `services.glpi-network.com` зависал, процесс php-fpm держал блокировку
  файла сессии, каждый заход в «Маркетплейс» добавлял ещё один зависший
  процесс; при `pm.max_children=10` пул кончился и сайт умер для всех,
  включая бота. Лечение: `pm.max_children=25` и
  `request_terminate_timeout=180` в `/etc/php/8.2/fpm/pool.d/www.conf`
  (бэкап рядом, `.bak-20260924`). Симптом в логах бота:
  `glpi_network_error ... attempt=3` и `sync_tick_failed`. Если повторится —
  смотреть `systemctl status php8.2-fpm` (строка Status: active/idle
  процессов) и `ps -o wchan -C php-fpm8.2` (`locks_lock_inode_wait` = блокировка
  сессии). Бот простой переживает корректно, данные не теряет.
- **Пользователь-дубль в AD.** У одного сотрудника было две учётки с
  одинаковым ФИО (кириллический `sAMAccountName` и нормальный), человек
  привязался не к той. В пик-листе теперь показывается логин при совпадении
  имён, но сам дубль в AD никто не убрал.
- **LDAP-синк в GLPI по расписанию не настроен.** Новые сотрудники не
  появляются в GLPI, пока не выполнить вручную:
  `sudo -u www-data php /var/www/glpi/bin/console glpi:ldap:synchronize_users --only-create-new -n`
  Стоит повесить в cron раз в час.
- Бот переживает перезапуски GLPI и Telegram-флуд (`TelegramRetryAfter`)
  без вмешательства — в логах это ожидаемый шум, не инцидент.

## 7. Git и публикация

- Remote: `origin` → `snnrman/glpi-tgbot` (приватный), `public` →
  `snnrman/glpigram` (публичный). Пушить нужно **в оба**.
- Trunk-based на `main`, CI (GitHub Actions) гоняет ruff + pytest на
  Python 3.11 и 3.12. Публичный CI виден через
  `https://api.github.com/repos/snnrman/glpigram/actions/runs`.
- **В сообщениях коммитов не должно быть трейлеров ассистента**
  (`Co-Authored-By: Claude …` и подобных) — владелец не хочет видеть
  ассистента в Contributors, историю ради этого уже переписывали.
- Доступ по SSH-ключу владельца из профиля GitHub; ключ **без парольной
  фразы** (ключ с забытой фразой месяц не давал пушить — проверяйте
  `ssh -T git@github.com`, должно быть `Hi snnrman!`).

## 8. Definition of done для любой правки

1. `ruff check bot tests` и `ruff format bot tests` — чисто.
2. `pytest -q` — всё зелёное, на новое поведение есть тест.
3. Обновлён `CHANGELOG.md` **и** `CHANGELOG.ru.md` (раздел `[Unreleased]`),
   при изменении архитектуры/особенностей — `CLAUDE.md`.
4. Коммит без трейлеров ассистента, пуш в `origin` и `public`.
5. `systemctl restart glpi-tgbot`, проверить `is-active` и логи за минуту.

Тесты — без сети: GLPI мокается через `respx`, Telegram — фейковым `Bot`,
который просто собирает отправленные сообщения. Смотреть образцы в
`tests/test_client.py` (API) и `tests/test_new_ticket.py` (диалоги).

## 9. Открытые хвосты

- **Обновить GLPI 11.0.8 → 11.0.9** — релиз безопасности (12 CVE, среди них
  неаутентифицированная SQL-инъекция и race condition в маркетплейсе).
  Не сделано.
- **77 обновлений пакетов ОС, 52 из них security** (PHP 8.2.29 → 8.2.32,
  nginx, openssl, openssh, systemd). Не сделано.
- **Отключить «Маркетплейс»** в GLPI — источник падения 24.09 и одной из
  дыр 11.0.9.
- **Родная инвентаризация включена** (`enabled_inventory=1`), эндпоинт
  `front/inventory.php` отвечает агентам, но агенты ещё не раскатаны
  (GLPI Agent 1.20). `stale_agents_delay=0` — задать, когда машины появятся.
- Трое лидов из `LEAD_LOGINS` не привязались (`/start`) — их нет в списке
  выбора.
- Версия в `pyproject.toml` (0.4.0) отстала от накопленного `[Unreleased]`;
  при следующем релизе поднять до 0.5.0 и проставить дату в changelog.

## 10. Идеи, обсуждавшиеся, но не реализованные

Нагрузка растёт (июль 82 заявки → август 115 → сентябрь 126+, ~6/день), и
доля «высокой» срочности выросла до 41% — люди её завышают. Обсуждали:

1. Светофор загруженности в начале `/new`: «в очереди N заявок, техников на
   линии M, берут в среднем за ~T».
2. Переименовать уровни срочности из степеней в ситуации: «не могу
   работать» / «мешает работать» / «когда будет время» + обещание сроков.
3. Кнопка «⬇️ Понизить срочность» у техника с тихим уведомлением заявителю.

Решения не принято — обсудить с владельцем перед реализацией.
